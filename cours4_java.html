Séquence 1 — 1 h 15

2. Hash SHA-256

2.1 — L'analogie : l'empreinte digitale d'un texte

Imaginez que vous deviez vérifier qu'un document n'a pas été modifié, sans comparer le document entier. Vous pourriez comparer une empreinte du document : un petit résumé qui dépend de tout le contenu. Si une seule lettre change, l'empreinte change. Si le document est identique, l'empreinte est identique.

C'est exactement ce que fait un hash cryptographique. Il prend en entrée un texte de n'importe quelle longueur et produit une empreinte de taille fixe. Pour SHA-256, cette empreinte fait 32 octets (256 bits), soit 64 caractères en hexadécimal.

Deux propriétés essentielles :

  • déterministe : le même texte donne toujours la même empreinte ;
  • non inversible : à partir de l'empreinte, on ne peut pas retrouver le texte d'origine.
Analogie — le hash d'un texte est comme l'empreinte digitale d'une personne. Elle est unique, stable, et on ne peut pas reconstruire la personne à partir de son empreinte.

2.2 — À quoi ça sert

UsageExplication
Vérifier l'intégrité d'un fichier téléchargé On compare le hash du fichier reçu avec le hash publié par l'éditeur.
Stocker un mot de passe On stocke le hash du mot de passe, jamais le mot de passe lui-même. À la connexion, on hache ce que l'utilisateur tape et on compare.
Identifier un contenu Git utilise SHA-1 pour identifier chaque commit et chaque fichier.
Détecter une altération Si le hash d'un message reçu diffère de celui attendu, le message a été modifié en route.

2.3 — Ce qu'un hash ne fait PAS

Un hash seul ne protège pas la confidentialité. Si vous publiez le hash d'un message, le message reste lisible par quiconque l'intercepte. Le hash ne fait que permettre de vérifier que le message n'a pas été altéré.

Un hash seul ne prouve pas non plus l'identité de l'expéditeur. N'importe qui peut calculer le hash d'un message. Pour prouver l'identité, il faut une clé secrète — c'est le rôle du HMAC (séquence 2).

2.4 — Le code Java

La classe MessageDigest calcule un hash. On la demande par son nom ("SHA-256"), on lui donne les octets du texte, et elle renvoie les 32 octets de l'empreinte. 

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

public class HashExample {
    public static void main(String[] args) throws NoSuchAlgorithmException {
        String texte = "Bonjour le monde";

        // 1. Obtenir l'algorithme
        MessageDigest md = MessageDigest.getInstance("SHA-256");

        // 2. Fournir les octets du texte
        byte[] octets = texte.getBytes(StandardCharsets.UTF_8);

        // 3. Calculer l'empreinte
        byte[] empreinte = md.digest(octets);

        // 4. Afficher en hexadécimal (64 caractères)
        String hex = HexFormat.of().formatHex(empreinte);
        System.out.println(hex);
    }
}

Lecture du code, ligne par ligne :

  • MessageDigest.getInstance("SHA-256") : on demande une instance de l'algorithme. Le nom est standard, il ne change pas.
  • texte.getBytes(UTF_8) : on convertit le texte en octets. L'encodage est important : le même texte encodé en UTF-8 ou en ISO-8859-1 donne des octets différents, donc un hash différent.
  • md.digest(octets) : calcule l'empreinte. La méthode consomme l'instance ; pour hacher un autre texte, il faut rappeler getInstance.
  • HexFormat.of().formatHex() : convertit les 32 octets en 64 caractères hexadécimaux.
Propriété — le hash dépend de l'encodage du texte. "café" en UTF-8 n'a pas le même hash que "café" en ISO-8859-1. Toujours préciser StandardCharsets.UTF_8.

Schéma 1 — Hash d'un texte

Le texte d'entrée, de longueur quelconque, est transformé par SHA-256 en une empreinte de 32 octets (64 caractères hexadécimaux). La moindre modification du texte change complètement l'empreinte.

2.5 — Piège : comparer des hash avec ==

Symptôme — deux hash identiques ne sont pas reconnus comme égaux.

Cause — comparer deux byte[] avec == compare les références, pas les contenus.

Remède — utiliser MessageDigest.isEqual(a, b), qui compare les contenus octet par octet et qui est résistant aux attaques par timing.

2.6 — Piège : utiliser MD5 ou SHA-1

Symptôme — un audit de sécurité signale l'usage de MD5 ou SHA-1.

Cause — ces algorithmes sont cassés : on peut produire deux textes différents avec le même hash (collision).

Remède — utiliser SHA-256 ou SHA-3. Vérifier dans le code avec grep "MD5\|SHA-1".

3. HMAC

3.1 — L'analogie : le sceau de cire

Un hash seul ne prouve pas qui a écrit le message. Si quelqu'un intercepte votre message et le hash, il peut modifier le message et recalculer un nouveau hash — vous n'y verrez que du feu.

Pour prouver l'identité de l'expéditeur, il faut une clé secrète partagée entre l'expéditeur et le destinataire. Le hash combiné à la clé s'appelle un HMAC (Hash-based Message Authentication Code). C'est comme un sceau de cire : le message peut être lu par tout le monde, mais seul celui qui possède le sceau peut l'apposer.

Analogie — le HMAC est au hash ce que le sceau de cire est à l'enveloppe. L'enveloppe peut être lue, mais seul le porteur du sceau peut garantir qu'elle vient bien de lui.

3.2 — Différence entre hash et HMAC

CritèreHashHMAC
Clé secrète Non Oui
Vérifie l'intégrité Oui Oui
Prouve l'identité Non Oui (celui qui possède la clé)
Peut être recalculé par un attaquant Oui Non (sans la clé)

3.3 — Le code Java

La classe Mac calcule un HMAC. On lui donne l'algorithme ("HmacSHA256") et la clé secrète, puis on lui fournit les octets du texte. 

import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.security.InvalidKeyException;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

public class HmacExample {
    public static void main(String[] args)
            throws NoSuchAlgorithmException, InvalidKeyException {
        String texte = "Bonjour le monde";
        byte[] cle = "cle-secrete-partagee".getBytes(StandardCharsets.UTF_8);

        // 1. Obtenir l'algorithme
        Mac mac = Mac.getInstance("HmacSHA256");

        // 2. Fournir la clé
        mac.init(new SecretKeySpec(cle, "HmacSHA256"));

        // 3. Calculer le HMAC
        byte[] hmac = mac.doFinal(texte.getBytes(StandardCharsets.UTF_8));

        // 4. Afficher en hexadécimal
        System.out.println(HexFormat.of().formatHex(hmac));
    }
}

Lecture du code :

  • Mac.getInstance("HmacSHA256") : HMAC utilisant SHA-256 comme fonction de hash interne.
  • mac.init(new SecretKeySpec(cle, ...)) : fournit la clé secrète. Les deux côtés doivent avoir exactement la même clé.
  • mac.doFinal(octets) : calcule le HMAC. Comme digest(), cette méthode consomme l'instance ; il faut rappeler init pour un nouveau calcul.
Propriété — la clé HMAC doit être longue et aléatoire (au moins 32 octets pour HmacSHA256). Une clé courte ou devinable annule la sécurité. Ne jamais coder la clé en dur dans le code source : la stocker dans une variable d'environnement ou un coffre-fort de secrets.

Schéma 2 — Hash versus HMAC

En haut, un hash simple : n'importe qui peut le recalculer. En bas, un HMAC : il faut la clé secrète partagée entre expéditeur et destinataire, donc un attaquant ne peut pas le recalculer.

3.4 — Piège : oublier de vérifier le HMAC

Symptôme — un message altéré est accepté.

Cause — le programme calcule le HMAC mais ne le compare pas à celui reçu.

Remède — toujours faire la comparaison avec MessageDigest.isEqual, et refuser le message si les HMAC diffèrent.

3.5 — Piège : réutiliser la même clé pour tout

Symptôme — une clé qui fuite compromet tout le système.

Cause — une seule clé HMAC pour tous les usages (authentification, signature de cookies, API).

Remède — une clé par usage. Une clé HMAC dédiée à chaque service. Rotation régulière.

4. AES-GCM — chiffrement symétrique

4.1 — L'analogie : le coffre-fort

Un chiffrement symétrique utilise une seule clé pour chiffrer et pour déchiffrer. C'est comme un coffre-fort : on a une combinaison (la clé), on ferme avec, on ouvre avec la même combinaison. Aucun des deux côtés n'a besoin de plus que la clé.

AES (Advanced Encryption Standard) est l'algorithme symétrique le plus utilisé au monde. Il existe en deux tailles principales : AES-128 (clé de 16 octets) et AES-256 (clé de 32 octets). On utilise aujourd'hui AES-256, car il offre une marge de sécurité confortable.

Analogie — AES est comme un coffre-fort très robuste. La clé est la combinaison. Perdre la clé, c'est perdre le contenu. La confier à quelqu'un, c'est lui donner accès au contenu.

4.2 — Le mode GCM

AES ne chiffre qu'un bloc de 16 octets à la fois. Pour chiffrer un texte plus long, il faut un mode d'opération. Les plus courants :

ModePropriétésRecommandé
ECB Chiffre chaque bloc indépendamment. Identique à un puzzle dont les pièces restent reconnaissables. À éviter absolument. Non
CBC Chaîne les blocs. Nécessite un IV aléatoire. Vérification d'intégrité séparée. Obsolète
GCM Chiffre et authentifie en une seule opération. Détecte toute altération. Rapide. Oui

GCM est aujourd'hui le mode par défaut recommandé. Il a un avantage décisif : il combine chiffrement et vérification d'intégrité. Si quelqu'un modifie un octet du message chiffré, GCM le détecte et lève une exception au déchiffrement. Pas besoin d'ajouter un HMAC séparé.

Propriété — GCM nécessite un IV (Initialization Vector, aussi appelé nonce) de 12 octets, unique pour chaque chiffrement avec la même clé. Réutiliser un IV avec la même clé casse complètement la sécurité.

4.3 — Le code Java

import javax.crypto.Cipher;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.security.SecureRandom;
import java.util.Base64;

public class AesExample {
    public static void main(String[] args) throws Exception {
        String texte = "Message confidentiel";
        byte[] cle = new byte[32]; // 32 octets = AES-256
        new SecureRandom().nextBytes(cle);

        // 1. Chiffrement
        byte[] iv = new byte[12];
        new SecureRandom().nextBytes(iv);

        Cipher chiffreur = Cipher.getInstance("AES/GCM/NoPadding");
        chiffreur.init(Cipher.ENCRYPT_MODE,
                       new SecretKeySpec(cle, "AES"),
                       new GCMParameterSpec(128, iv));

        byte[] chiffre = chiffreur.doFinal(texte.getBytes(StandardCharsets.UTF_8));

        System.out.println("Chiffre (base64) : " + Base64.getEncoder().encodeToString(chiffre));

        // 2. Déchiffrement
        Cipher dechiffreur = Cipher.getInstance("AES/GCM/NoPadding");
        dechiffreur.init(Cipher.DECRYPT_MODE,
                         new SecretKeySpec(cle, "AES"),
                         new GCMParameterSpec(128, iv));

        byte[] dechiffre = dechiffreur.doFinal(chiffre);
        System.out.println("Déchiffré : " + new String(dechiffre, StandardCharsets.UTF_8));
    }
}

Lecture du code :

  • new byte[32] puis SecureRandom().nextBytes(cle) : clé AES-256 aléatoire. Ne jamais utiliser Random (non cryptographique) ; utiliser SecureRandom.
  • new byte[12] : IV de 12 octets, généré aléatoirement à chaque chiffrement.
  • Cipher.getInstance("AES/GCM/NoPadding") : algorithme/mode/padding. GCM n'utilise pas de padding (d'où NoPadding).
  • GCMParameterSpec(128, iv) : le 128 est la taille du tag d'authentification en bits. 128 est la valeur standard.
  • doFinal : effectue le chiffrement (ou le déchiffrement). Lève AEADBadTagException si l'intégrité est compromise au déchiffrement.

Schéma 3 — Chiffrement symétrique AES-GCM

La même clé sert à chiffrer et à déchiffrer. L'IV est généré aléatoirement à chaque chiffrement et transmis avec le message. GCM ajoute un tag d'authentification pour détecter toute altération.

4.4 — Piège : réutiliser l'IV

Symptôme — un audit signale « IV reuse ». Pire : deux messages chiffrés avec le même IV et la même clé peuvent être déchiffrés sans la clé.

Cause — l'IV a été codé en dur ou généré une seule fois au démarrage.

Remède — générer un nouvel IV aléatoire à chaque chiffrement, avec SecureRandom. Transmettre l'IV avec le message (il n'est pas secret).

4.5 — Piège : utiliser Random au lieu de SecureRandom

Symptôme — un audit signale « weak random ».

Cause — java.util.Random est un générateur pseudo-aléatoire déterministe : connaissant l'état interne, on peut prédire les valeurs suivantes.

Remède — utiliser java.security.SecureRandom pour toute valeur secrète (clé, IV, sel, nonce).

4.6 — Piège : ignorer AEADBadTagException

Symptôme — un message altéré est déchiffré comme si de rien n'était (ou plante avec une exception non gérée).

Cause — GCM lève une exception si l'intégrité est compromise ; l'exception n'est pas attrapée.

Remède — entourer le doFinal de déchiffrement d'un try/catch (AEADBadTagException) et traiter le cas comme un message invalide, sans donner de détail à l'utilisateur.

5. RSA — chiffrement asymétrique

5.1 — L'analogie : la boîte aux lettres

Un chiffrement asymétrique utilise deux clés différentes : une clé publique et une clé privée. Ce qui est chiffré avec la clé publique ne peut être déchiffré qu'avec la clé privée correspondante. Et inversement.

C'est comme une boîte aux lettres publique : tout le monde peut y déposer un courrier (chiffrer avec la clé publique), mais seul le propriétaire peut l'ouvrir (déchiffrer avec la clé privée). La clé publique est publiée partout, la clé privée reste secrète.

Analogie — RSA est comme une boîte aux lettres publique. La fente est accessible à tous (clé publique), mais seul le propriétaire a la clef de la boîte (clé privée).

5.2 — Pourquoi RSA n'est pas utilisé pour chiffrer du texte long

RSA est très lent comparé à AES. De plus, il ne peut chiffrer qu'un texte plus court que la taille de la clé (moins le padding). Pour une clé de 2048 bits, on ne peut chiffrer qu'environ 190 octets.

En pratique, on n'utilise RSA que pour deux choses :

  • Chiffrer une clé AES (32 octets), qu'on utilise ensuite pour chiffrer le vrai message. C'est le principe hybride, utilisé par TLS.
  • Signer un hash (32 octets) pour prouver l'identité de l'expéditeur.

Chiffrer un texte long directement avec RSA est une erreur. On ne le fait jamais en pratique. On le montre ici uniquement pour comprendre le mécanisme.

5.3 — Le code Java

import javax.crypto.Cipher;
import java.nio.charset.StandardCharsets;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.util.Base64;

public class RsaExample {
    public static void main(String[] args) throws Exception {
        // 1. Générer une paire de clés (2048 bits)
        KeyPairGenerator gen = KeyPairGenerator.getInstance("RSA");
        gen.initialize(2048);
        KeyPair paire = gen.generateKeyPair();

        String texte = "Message court";

        // 2. Chiffrer avec la clé publique
        Cipher chiffreur = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        chiffreur.init(Cipher.ENCRYPT_MODE, paire.getPublic());
        byte[] chiffre = chiffreur.doFinal(texte.getBytes(StandardCharsets.UTF_8));

        System.out.println("Chiffré (base64) : " + Base64.getEncoder().encodeToString(chiffre));

        // 3. Déchiffrer avec la clé privée
        Cipher dechiffreur = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        dechiffreur.init(Cipher.DECRYPT_MODE, paire.getPrivate());
        byte[] dechiffre = dechiffreur.doFinal(chiffre);

        System.out.println("Déchiffré : " + new String(dechiffre, StandardCharsets.UTF_8));
    }
}

Lecture du code :

  • KeyPairGenerator.getInstance("RSA") puis initialize(2048) : génère une paire de clés RSA de 2048 bits. C'est la taille minimale recommandée aujourd'hui.
  • paire.getPublic() et paire.getPrivate() : les deux clés.
  • RSA/ECB/OAEPWithSHA-256AndMGF1Padding : algorithme RSA avec le padding OAEP, obligatoire en pratique. Sans padding (NoPadding), RSA est vulnérable.
  • doFinal : comme pour AES, effectue le chiffrement ou déchiffrement.

Schéma 4 — Chiffrement asymétrique RSA

La clé publique est utilisée pour chiffrer, la clé privée pour déchiffrer. La clé publique peut être publiée partout, la clé privée reste secrète. C'est le principe de la boîte aux lettres.

5.4 — Le modèle hybride

Pour chiffrer un texte long en pratique, on combine les deux approches :

  1. Générer une clé AES aléatoire (32 octets).
  2. Chiffrer le texte avec AES-GCM.
  3. Chiffrer la clé AES avec RSA.
  4. Transmettre : clé AES chiffrée + message chiffré.

C'est ce que fait TLS, c'est ce que font tous les systèmes réels. RSA résout le problème du partage de clé ; AES résout le problème de la performance.

Schéma 5 — Modèle hybride RSA + AES

Une clé AES est générée aléatoirement. Elle chiffre le message avec AES-GCM. Elle est elle-même chiffrée avec RSA et transmise avec le message. Le destinataire déchiffre la clé AES avec sa clé privée, puis le message avec la clé AES.

5.5 — Piège : utiliser NoPadding

Symptôme — un audit signale « RSA without padding ».

Cause — RSA sans padding est vulnérable à des attaques permettant de déchiffrer des messages ou de forger des signatures.

Remède — toujours utiliser RSA/ECB/OAEPWithSHA-256AndMGF1Padding (chiffrement) ou un padding de signature adapté.

5.6 — Piège : utiliser une clé RSA trop courte

Symptôme — un audit signale « RSA key size too small ».

Cause — des clés de 1024 bits ou moins sont considérées comme cassables à moyen terme.

Remède — minimum 2048 bits. 4096 pour les systèmes à longue durée de vie.

5.7 — Piège : chiffrer du texte long directement avec RSA

Symptôme — IllegalBlockSizeException: Data must not be longer than ....

Cause — RSA ne peut chiffrer qu'un bloc de taille limitée (moins que la taille de la clé, moins le padding).

Remède — utiliser le modèle hybride (AES pour le texte, RSA pour la clé AES).

Séquence 5 — 1 h 30

6. Encodage et transport

6.1 — Le problème : du binaire dans du texte

Un message chiffré est une suite d'octets arbitraires. Ces octets peuvent contenir n'importe quelle valeur de 0x00 à 0xFF. Or, les protocoles textuels (JSON, XML, URL, email, HTTP headers) ne peuvent transporter que des caractères imprimables.

Si vous mettez des octets binaires dans du JSON sans les encoder, vous obtenez des erreurs de parsing ou des corruptions. Il faut encoder le binaire en texte, d'une manière qui soit réversible.

6.2 — Base64

Base64 est le standard pour cela. Il transforme 3 octets binaires en 4 caractères ASCII (lettres, chiffres, +, /, avec = pour le padding). Le message encodé fait environ 33% plus long que le message original, mais reste entièrement textuel.

Schéma 6 — Encodage base64

Trois octets binaires (24 bits) sont découpés en quatre groupes de 6 bits, chacun converti en un caractère ASCII imprimable. Le résultat est 33% plus long, mais entièrement transportable en JSON, URL, email, etc.

6.3 — Utilisation en Java

import java.util.Base64;

byte[] binaire = ...;
String texte = Base64.getEncoder().encodeToString(binaire);

byte[] decode = Base64.getDecoder().decode(texte);

// Variante pour URL (remplace + et / par - et _)
String urlSafe = Base64.getUrlEncoder().encodeToString(binaire);

Il existe trois variantes :

MéthodeUsage
getEncoder()Standard, pour JSON, email
getUrlEncoder()Pour les URL et noms de fichiers (+ → -, / → _)
getMimeEncoder()Pour l'email, avec sauts de ligne

6.4 — Le format typique d'un message chiffré transporté

Quand on transporte un message chiffré, on transmet généralement deux choses :

  • l'IV (ou le nonce), en base64 ;
  • le chiffré, en base64.

Les deux peuvent être combinés dans une seule chaîne, ou dans un objet JSON. Exemple : 

{
  "iv": "AQIz7bF9kL2pQ3xY...",
  "ciphertext": "kL3pQ7xY+9aB...",
  "algorithm": "AES-256-GCM"
}

C'est ce type de structure qu'on retrouve dans les API REST, dans les tokens JWT, dans les messages d'un protocole applicatif.

6.5 — Piège : confondre encodage et chiffrement

Symptôme — un message sensible est publié en base64 en croyant qu'il est chiffré.

Cause — base64 n'est pas un chiffrement. C'est un encodage réversible sans clé : n'importe qui peut décoder.

Remède — base64 ne protège rien. Il sert uniquement à transporter du binaire dans du texte. Pour protéger, il faut chiffrer (AES, RSA) avant d'encoder en base64.

6.6 — Piège : oublier de transmettre l'IV

Symptôme — impossible de déchiffrer un message AES-GCM reçu.

Cause — l'IV n'a pas été transmis. Il est indispensable au déchiffrement.

Remède — toujours transmettre l'IV avec le chiffré. L'IV n'est pas secret, il peut être public.

8. Bilan — Jour 4

  • Un hash vérifie l'intégrité d'un texte, mais ne prouve pas l'identité de l'expéditeur.
  • Un HMAC ajoute une clé secrète au hash, ce qui prouve l'identité de l'expéditeur.
  • AES-GCM chiffre et authentifie en une seule opération. C'est le mode recommandé aujourd'hui.
  • RSA est asymétrique : la clé publique chiffre, la clé privée déchiffre. Il est lent et ne sert qu'à échanger des clés ou signer.
  • Le modèle hybride combine AES pour le texte et RSA pour la clé AES. C'est ce que fait TLS.
  • Base64 encode du binaire en texte, sans le chiffrer. C'est un encodage, pas un chiffrement.
  • Les pièges à éviter : réutiliser l'IV, utiliser Random, RSA sans padding, croire que base64 chiffre.

Ce qu'on n'a pas fait

Cette journée s'est concentrée sur les quatre briques de la cryptographie appliquée. On n'a pas couvert :

  • TLS — comment ces briques s'assemblent dans un protocole réseau complet. À voir en spécialisation.
  • Certificats X.509 et PKI — comment on fait confiance à une clé publique. À voir en spécialisation.
  • Signature numérique — usage de RSA pour signer. Mentionné, non pratiqué.
  • Stockage de mots de passe (bcrypt, Argon2) — usage du hash en pratique. Mentionné, non pratiqué.
