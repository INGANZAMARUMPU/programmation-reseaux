2. Notion de socket

2.1 — Définition

Une socket est une abstraction fournie par le système d'exploitation qui représente une extrémité de communication entre deux programmes. Elle est identifiée par un triplet (adresse IP, port, protocole de transport).

Du point de vue du programmeur, une socket est un objet sur lequel on peut lire et écrire. Du point de vue du système, c'est une structure de données interne associée à un descripteur de fichier. Une même application peut ouvrir plusieurs sockets simultanément.

Remarque — une socket n'est ni un câble, ni une connexion. C'est une extrémité. Une connexion TCP est identifiée par un couple de sockets (une par extrémité), soit un quadruplet (IP source, port source, IP destination, port destination).

2.2 — Identifiants d'une socket

ÉlémentRôleExemple
Adresse IP Identifie la machine sur le réseau 192.168.1.10, 127.0.0.1
Port Identifie le processus sur la machine (16 bits, 0–65535) 80, 443, 9000
Protocole de transport Détermine le mode de communication TCP ou UDP

Le couple (IP, port) est unique à un instant donné sur une machine, pour un protocole donné. Deux processus ne peuvent pas écouter sur le même port avec le même protocole. En revanche, TCP et UDP peuvent partager le même numéro de port sans conflit : ils appartiennent à deux espaces distincts.

2.3 — Ports réservés et ports dynamiques

PlageNomUsage
0 – 1023Ports bien connusServices standards (80, 443, 22…)
1024 – 49151Ports enregistrésApplications connues
49152 – 65535Ports dynamiquesAlloués automatiquement côté client

Sous Linux, les ports inférieurs à 1024 nécessitent des privilèges root. En pratique, on développe sur des ports supérieurs (8000, 9000, etc.).

2.4 — Adresses particulières

AdresseSignification
127.0.0.1Boucle locale (loopback) — la machine elle-même
0.0.0.0Toutes les interfaces — pour un serveur qui écoute partout
255.255.255.255Diffusion limitée au réseau local
À retenir — un serveur qui écoute sur 0.0.0.0 accepte les connexions sur toutes ses interfaces réseau (loopback, Ethernet, Wi-Fi…). Un serveur qui écoute sur 127.0.0.1 n'accepte que les connexions locales, ce qui est plus sûr en développement.

3.2 — Cycle de vie d'une connexion

Schéma 1 — Cycle de vie d'une connexion TCP

Ouverture en trois temps (SYN, SYN/ACK, ACK), échange de données, puis fermeture négociée (FIN, ACK, FIN, ACK).

L'établissement d'une connexion TCP se fait en trois segments (three-way handshake) :

  1. Le client envoie un segment SYN (synchronisation) avec son numéro de séquence initial.
  2. Le serveur répond par un SYN/ACK acquittant le SYN du client et proposant son propre numéro de séquence.
  3. Le client confirme par un ACK.

La fermeture est également négociée, en quatre segments (chaque extrémité ferme son propre sens de communication). Cette symétrie explique l'apparition de l'état TIME_WAIT côté client, qui persiste environ deux minutes après la fermeture.

3.3 — États d'une socket TCP

Schéma 2 — États d'une socket TCP (côté serveur)

États principaux : CLOSED, LISTEN, SYN_RECEIVED, ESTABLISHED, CLOSE_WAIT, LAST_ACK. Les transitions correspondent aux appels Java et aux segments reçus.

L'état ESTABLISHED est le seul où les données circulent normalement. L'état CLOSE_WAIT indique que le pair a fermé son côté, mais que l'application locale n'a pas encore appelé close().

À retenir — côté serveur, l'ordre des appels est new ServerSocket(port) puis serverSocket.accept(). Côté client : new Socket(hôte, port).

4.4 — Flux d'entrée / sortie

Java ne manipule pas directement des sockets pour les données : on passe par des flux (InputStream, OutputStream). Ces flux sont obtenus une seule fois par socket et réutilisés. 

Socket socket = new Socket("127.0.0.1", 9000);

InputStream in = socket.getInputStream();
OutputStream out = socket.getOutputStream();

// Écriture
byte[] donnees = "Bonjour".getBytes(StandardCharsets.UTF_8);
out.write(donnees);
out.flush();   // indispensable

// Lecture
byte[] buffer = new byte[1024];
int n = in.read(buffer);   // renvoie -1 si fin de flux
Propriété — en Java, OutputStream est souvent tamponné. Il faut appeler flush() après chaque écriture pour forcer l'envoi effectif des octets.

4.5 — Encodage des chaînes

String.getBytes() utilise l'encodage par défaut de la plateforme, qui peut varier. Il faut toujours spécifier explicitement StandardCharsets.UTF_8. 

String message = "Bonjour";

// Encodage explicite (bonne pratique)
byte[] donnees = message.getBytes(StandardCharsets.UTF_8);

// Décodage explicite
String texte = new String(donnees, StandardCharsets.UTF_8);

4.6 — Sémantique de read()

Propriété — InputStream.read(byte[]) renvoie le nombre d'octets lus, ou -1 si la fin du flux est atteinte (équivalent de b"" en Python). Il peut renvoyer moins que la taille du tampon.

Deux conséquences pratiques :

  • un appel à write() ne correspond pas nécessairement à un appel à read() ;
  • pour lire une quantité fixe d'octets, il faut boucler jusqu'à l'avoir obtenue.
/**
 * Lit exactement n octets, ou lève une IOException si la connexion se ferme.
 */
public static byte[] readExactly(InputStream in, int n) throws IOException {
    byte[] donnees = new byte[n];
    int lus = 0;
    while (lus < n) {
        int r = in.read(donnees, lus, n - lus);
        if (r == -1) {
            throw new IOException("connexion fermée avant réception complète");
        }
        lus += r;
    }
    return donnees;
}

4.7 — Détection de fermeture

read() qui renvoie -1 signale que le pair a fermé la connexion. C'est la méthode canonique de détection, et elle ne lève pas d'exception. 

int n = in.read(buffer);
if (n == -1) {
    System.out.println("connexion fermée par le pair");
}

4.8 — Timeout

Par défaut, les opérations bloquantes (accept(), read()) attendent indéfiniment. On fixe un délai maximal avec setSoTimeout() (en millisecondes). 

socket.setSoTimeout(5000);   // 5 secondes

try {
    int n = in.read(buffer);
} catch (SocketTimeoutException e) {
    System.out.println("délai dépassé");
}

setSoTimeout(0) rétablit le mode bloquant.

4.9 — Réutilisation d'adresse

Après la fermeture d'un serveur, le port reste dans l'état TIME_WAIT pendant environ deux minutes. Tenter de relancer le serveur immédiatement échoue avec BindException. 

ServerSocket server = new ServerSocket();
server.setReuseAddress(true);
server.bind(new InetSocketAddress(9000));

Contrairement à Python, en Java il faut créer le ServerSocket avec le constructeur sans argument, appeler setReuseAddress(true), puis bind(). Si on utilise new ServerSocket(port), le bind est déjà effectué.

4.10 — Exemple complet : serveur et client TCP

Ce couple d'exemples illustre l'ensemble des notions ci-dessus. Il servira de référence pour les TP.

Serveur — ServeurEcho.java

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class ServeurEcho {

    public static void main(String[] args) throws IOException {
        ServerSocket server = new ServerSocket();
        server.setReuseAddress(true);
        server.bind(new InetSocketAddress("0.0.0.0", 9000));
        System.out.println("[serveur] écoute sur 9000");

        try (Socket conn = server.accept()) {
            conn.setSoTimeout(10000);
            System.out.println("[serveur] client " + conn.getRemoteSocketAddress());

            InputStream in = conn.getInputStream();
            OutputStream out = conn.getOutputStream();
            byte[] buffer = new byte[1024];

            int n;
            while ((n = in.read(buffer)) != -1) {
                System.out.println("[serveur] reçu " + n + " octets");
                out.write(buffer, 0, n);
                out.flush();
            }
            System.out.println("[serveur] client déconnecté");
        } finally {
            server.close();
        }
    }
}

Client — ClientEcho.java

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class ClientEcho {

    public static void main(String[] args) throws IOException {
        try (Socket socket = new Socket("127.0.0.1", 9000)) {
            socket.setSoTimeout(5000);
            System.out.println("[client] connecté");

            InputStream in = socket.getInputStream();
            OutputStream out = socket.getOutputStream();

            byte[] message = "Bonjour serveur".getBytes(StandardCharsets.UTF_8);
            out.write(message);
            out.flush();

            byte[] buffer = new byte[1024];
            int n = in.read(buffer);
            if (n == -1) {
                System.out.println("[client] connexion fermée");
            } else {
                String reponse = new String(buffer, 0, n, StandardCharsets.UTF_8);
                System.out.println("[client] réponse : " + reponse);
            }
        }
    }
}

5. Erreurs réseau courantes en Java

Un programme réseau doit anticiper les erreurs. Contrairement à un programme local, il dépend d'un environnement non maîtrisé : le réseau, l'autre machine, la disponibilité du service.

5.1 — Catalogue des exceptions

ExceptionCauseRemède
ConnectException Serveur non lancé, port erroné, ou rejet explicite Vérifier l'état du serveur, le port
SocketTimeoutException Pas de réponse dans le délai imparti setSoTimeout(), try/catch
BindException Port déjà occupé (état TIME_WAIT) setReuseAddress(true)
SocketException Connexion fermée brutalement, ou socket invalide Gérer dans try/catch, fermer proprement
UnknownHostException Échec de résolution de nom (DNS) Vérifier le nom d'hôte, la connexion DNS
NoRouteToHostException Route absente vers la destination Vérifier la configuration réseau
EOFException Fin de flux prématurée (via DataInputStream) Détecter la fermeture avant lecture

5.2 — Hiérarchie des exceptions

La plupart des exceptions réseau héritent de IOException. Il est possible de les intercepter toutes ensemble, ou individuellement. 

try {
    Socket socket = new Socket("127.0.0.1", 9000);
    // ...
} catch (ConnectException e) {
    System.err.println("connexion refusée : " + e.getMessage());
} catch (SocketTimeoutException e) {
    System.err.println("timeout : " + e.getMessage());
} catch (IOException e) {
    System.err.println("erreur d'E/S : " + e.getMessage());
}

5.3 — Structure canonique d'un serveur robuste

import java.io.*;
import java.net.*;

public class ServeurRobuste {
    public static void main(String[] args) {
        ServerSocket server = null;
        try {
            server = new ServerSocket();
            server.setReuseAddress(true);
            server.bind(new InetSocketAddress("0.0.0.0", 9000));

            try (Socket conn = server.accept()) {
                conn.setSoTimeout(10000);
                InputStream in = conn.getInputStream();
                OutputStream out = conn.getOutputStream();
                byte[] buffer = new byte[1024];

                while (true) {
                    int n;
                    try {
                        n = in.read(buffer);
                    } catch (SocketTimeoutException e) {
                        System.err.println("timeout sur read()");
                        break;
                    }
                    if (n == -1) break;

                    try {
                        out.write(buffer, 0, n);
                        out.flush();
                    } catch (IOException e) {
                        System.err.println("erreur d'écriture : " + e.getMessage());
                        break;
                    }
                }
            }
        } catch (IOException e) {
            System.err.println("erreur serveur : " + e.getMessage());
        } finally {
            if (server != null && !server.isClosed()) {
                try { server.close(); } catch (IOException ignored) {}
            }
        }
    }
}

Le bloc finally garantit la libération des ressources, même en cas d'erreur. Le try-with-resources sur Socket ferme automatiquement la connexion.

5.4 — try/finally versus try-with-resources

Java 7 a introduit le try-with-resources, qui ferme automatiquement les ressources implémentant AutoCloseable. C'est la forme moderne et recommandée. 

// Ancienne forme — try/finally explicite
Socket socket = null;
try {
    socket = new Socket("127.0.0.1", 9000);
    // ...
} finally {
    if (socket != null) socket.close();
}

// Forme moderne — try-with-resources
try (Socket socket = new Socket("127.0.0.1", 9000)) {
    // ...
}

6.3 — Exemple complet : serveur et client UDP

Serveur UDP — ServeurUdp.java

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class ServeurUdp {

    public static void main(String[] args) throws IOException {
        DatagramSocket socket = new DatagramSocket(9001);
        System.out.println("[serveur UDP] écoute sur 9001");

        byte[] buffer = new byte[1024];

        while (true) {
            DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
            socket.receive(packet);

            String message = new String(packet.getData(), 0, packet.getLength(),
                                        StandardCharsets.UTF_8);
            System.out.println("[serveur UDP] " + packet.getSocketAddress()
                               + " : " + message);

            // Écho : renvoyer le même datagramme à l'expéditeur
            socket.send(packet);
        }
    }
}

Client UDP — ClientUdp.java

import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class ClientUdp {

    public static void main(String[] args) throws IOException {
        DatagramSocket socket = new DatagramSocket();
        socket.setSoTimeout(3000);

        byte[] message = "ping UDP".getBytes(StandardCharsets.UTF_8);
        InetAddress adresse = InetAddress.getByName("127.0.0.1");
        DatagramPacket paquet = new DatagramPacket(message, message.length,
                                                   adresse, 9001);
        socket.send(paquet);

        byte[] buffer = new byte[1024];
        DatagramPacket reponse = new DatagramPacket(buffer, buffer.length);

        try {
            socket.receive(reponse);
            String texte = new String(reponse.getData(), 0,
                                      reponse.getLength(),
                                      StandardCharsets.UTF_8);
            System.out.println("[client UDP] réponse : " + texte);
        } catch (SocketTimeoutException e) {
            System.out.println("[client UDP] pas de réponse");
        }

        socket.close();
    }
}

6.4 — Différences fondamentales TCP / UDP

CritèreTCPUDP
ÉtablissementOui (handshake)Non
EnvoiOutputStream.writeDatagramSocket.send
RéceptionInputStream.readDatagramSocket.receive
FrontièresNonOui
Détection de perteAutomatiqueAucune
Signalement de fermetureread() == -1Impossible à détecter
Cas d'usageHTTP, SSH, transfert de fichiersDNS, VoIP, jeux, streaming
Propriété — en UDP, l'absence de réponse n'est pas détectable par le protocole. Si un datagramme est perdu, l'application attend indéfiniment. Seul un timeout applicatif permet de détecter la perte.

6.5 — Taille d'un datagramme

La taille maximale d'un datagramme UDP est théoriquement de 65507 octets (limite du protocole IP). En pratique, on dépasse rarement 1472 octets (MTU Ethernet 1500 – en-têtes IP et UDP). Au-delà, la fragmentation IP dégrade les performances et augmente les risques de perte.

7. Pièges et erreurs courantes en Java

Cette section recense les erreurs les plus fréquentes rencontrées par les étudiants lors de l'écriture de programmes réseau en Java. Chaque piège est présenté sous la forme symptôme → cause → remède.

7.1 — Piège : oublier flush()

Symptôme — le client envoie un message, mais le serveur ne reçoit rien.

Cause — OutputStream est souvent tamponné. Les octets restent en mémoire tant que flush() n'est pas appelé.

Remède — appeler out.flush() après chaque write().

7.2 — Piège : oublier l'encodage explicite

Symptôme — les caractères accentués sont corrompus d'une machine à l'autre.

Cause — String.getBytes() sans argument utilise l'encodage par défaut de la plateforme, qui peut différer.

Remède — toujours spécifier StandardCharsets.UTF_8.

7.3 — Piège : croire que read() lit tout

Symptôme — un message long arrive tronqué, ou une partie du message suivant est collée au premier.

Cause — read() renvoie jusqu'à la taille du tampon, pas exactement cette taille. C'est le comportement du flux TCP.

Remède — boucler jusqu'à avoir la quantité désirée, ou utiliser un délimiteur, ou préfixer par une longueur.

7.4 — Piège : confondre accept() et le socket de communication

Symptôme — le serveur ne peut pas accepter un second client.

Cause — accept() renvoie un nouveau Socket dédié à la communication. Le ServerSocket reste disponible pour d'autres accept().

Remède — bien distinguer ServerSocket server (écoute) et Socket conn (communication).

7.5 — Piège : oublier setReuseAddress

Symptôme — java.net.BindException: Address already in use au redémarrage du serveur.

Cause — le port est encore en TIME_WAIT après la fermeture.

Remède — utiliser le constructeur sans argument puis setReuseAddress(true) avant bind().

7.6 — Piège : ne pas gérer la fermeture

Symptôme — boucle infinie dans le serveur, ou SocketException lors d'un envoi.

Cause — read() == -1 non détecté, ou écriture sur un socket fermé.

Remède — tester if (n == -1) break; après chaque read(). Envelopper les écritures dans un try/catch sur IOException.

7.7 — Piège : bloquer indéfiniment sur read()

Symptôme — le programme ne répond plus, impossible de l'interrompre proprement.

Cause — read() sans timeout attend indéfiniment.

Remède — setSoTimeout(ms) et gérer SocketTimeoutException.

7.8 — Piège : croire qu'UDP signale les pertes

Symptôme — le client UDP attend indéfiniment alors que le serveur n'est pas lancé.

Cause — UDP n'a aucun mécanisme de retour. Un datagramme vers un port fermé génère un message ICMP port unreachable, mais celui-ci n'est pas remonté à l'application par défaut.

Remède — prévoir un timeout applicatif avec setSoTimeout() et une stratégie de retransmission si nécessaire.

7.9 — Piège : réutiliser un socket fermé

Symptôme — java.net.SocketException: Socket is closed.

Cause — un socket fermé ne peut plus être utilisé. Il doit être recréé.

Remède — vérifier le cycle de vie. En cas de reconnexion, créer un nouveau Socket.

7.10 — Piège : read() avec un tampon trop petit

Symptôme — les messages longs sont tronqués.

Cause — read(buffer) ne lit que buffer.length octets au maximum, le reste reste dans le tampon.

Remède — dimensionner le tampon en fonction du protocole, ou boucler jusqu'à épuisement.

7.11 — Piège : utiliser PrintWriter sans autoFlush

Symptôme — les messages textuels n'arrivent pas, malgré un println().

Cause — PrintWriter est tamponné. Par défaut, autoFlush est à false.

Remède — créer avec new PrintWriter(out, true) (le second argument active l'autoFlush), ou appeler flush() explicitement.

8. TP 1 — Client et serveur d'écho TCP

Facile

Objectif

9. TP 2 — Robustesse et gestion des erreurs

Moyen

Objectif

Reprendre le TP1 et le rendre tolérant aux erreurs réseau décrites en section 5. L'objectif est qu'aucune situation anormale ne provoque un crash.

Cahier des charges

Serveur

  • Timeout de 10 secondes sur read() avec setSoTimeout(10000).
  • Boucle de lecture jusqu'à ce que le client ferme (read() == -1).
  • Gestion explicite de SocketTimeoutException et SocketException.
  • Bloc finally garantissant la fermeture du ServerSocket.

11. TP 4 — Mini-protocole applicatif

Difficile

Objectif

Concevoir et implémenter un protocole applicatif simple : un serveur de calcul qui reçoit des opérations et renvoie le résultat ou un message d'erreur. Ce TP mobilise l'ensemble des notions de la journée.

Spécification du protocole

RequêteRéponse attendue

div 10 0ERROR division par zéro
add 3ERROR format invalide

Les messages sont encodés en UTF-8. Chaque requête tient sur une ligne terminée par un saut de ligne. Le serveur répond par une ligne, terminée également par un saut de ligne.

Cahier des charges

Serveur TCP — ServeurCalc.java

  • Écouter sur le port 9002 avec setReuseAddress(true).
  • Accepter une connexion, puis traiter les requêtes successives jusqu'à fermeture par le client.

  • Gérer les erreurs de format et les opérations inconnues.
  • Utiliser un timeout de 10 secondes et gérer SocketTimeoutException.
  • Encoder les réponses en UTF-8 et appeler flush().

Client TCP — ClientCalc.java

  • Se connecter à 127.0.0.1:9002.
  • Boucler : lire une ligne au clavier (avec BufferedReader sur System.in), l'encoder en UTF-8, l'envoyer avec un saut de ligne, flush(), attendre la réponse, l'afficher.

12. À retenir — Jour 1

  • Une socket est une extrémité de communication identifiée par un triplet (adresse IP, port, protocole).
  • TCP est connecté, fiable, ordonné, sans frontières de message. UDP est non connecté, non fiable, avec frontières de message.
  • Côté serveur TCP : new ServerSocket (avec setReuseAddress) → accept().
  • Côté client TCP : new Socket(hôte, port).
  • Côté serveur UDP : new DatagramSocket(port). Côté client UDP : new DatagramSocket().
  • En Java, on n'écrit pas directement sur la socket : on passe par getInputStream() et getOutputStream().
  • Toujours flush() après écriture.
  • Toujours spécifier StandardCharsets.UTF_8 pour l'encodage.
  • read() peut renvoyer moins que la taille du tampon. Pour lire une quantité fixe, boucler.
  • read() == -1 signale la fermeture de la connexion par le pair.
  • Prévoir systématiquement setSoTimeout(), try/catch et finally: close().
  • setReuseAddress(true) évite BindException au redémarrage.
  • UDP ne signale pas les pertes : seul un timeout applicatif permet de les détecter.
  • accept() renvoie un nouveau Socket, distinct du ServerSocket d'écoute.
