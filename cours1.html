2. Notion de socket

2.1 — Définition

Une socket est une abstraction fournie par le système d'exploitation qui représente une extrémité de communication entre deux programmes. Elle est identifiée par un triplet (adresse IP, port, protocole de transport).

Du point de vue du programmeur, une socket est un objet sur lequel on peut lire et écrire. Du point de vue du système, c'est une structure de données interne associée à un descripteur de fichier. Une même application peut ouvrir plusieurs sockets simultanément.

Remarque — une socket n'est ni un câble, ni une connexion. C'est une extrémité. Une connexion TCP est identifiée par un couple de sockets (une par extrémité), soit un quadruplet (IP source, port source, IP destination, port destination).

2.2 — Identifiants d'une socket

ÉlémentRôleExemple
Adresse IP Identifie la machine sur le réseau 192.168.1.10, 127.0.0.1
Port Identifie le processus sur la machine (16 bits, 0–65535) 80, 443, 9000
Protocole de transport Détermine le mode de communication TCP ou UDP

Le couple (IP, port) est unique à un instant donné sur une machine, pour un protocole donné. Deux processus ne peuvent pas écouter sur le même port avec le même protocole. En revanche, TCP et UDP peuvent partager le même numéro de port sans conflit : ils appartiennent à deux espaces distincts.

2.3 — Ports réservés et ports dynamiques

PlageNomUsage
0 – 1023Ports bien connusServices standards (80, 443, 22…)
1024 – 49151Ports enregistrésApplications connues
49152 – 65535Ports dynamiquesAlloués automatiquement côté client

Sous Linux, les ports inférieurs à 1024 nécessitent des privilèges root. En pratique, on développe sur des ports supérieurs (8000, 9000, etc.).

2.4 — Domaines d'adresses

2.5 — Adresses particulières

À retenir — un serveur qui écoute sur 0.0.0.0 accepte les connexions sur toutes ses interfaces réseau (loopback, Ethernet, Wi-Fi…). Un serveur qui écoute sur 127.0.0.1 n'accepte que les connexions locales, ce qui est plus sûr en développement.

3. TCP : le mode connecté

3.1 — Propriétés

PropriétéTCP
TypeOrienté connexion (flux d'octets)
FiabilitéGarantie (retransmission, accusés de réception)
OrdrePréservé
Frontières de messageAbsentes — TCP est un flux continu
Contrôle de fluxOui (fenêtre glissante)
Contrôle de congestionOui (slow start, congestion avoidance)
Constante PythonSOCK_STREAM

3.2 — Cycle de vie d'une connexion

Schéma 1 — Cycle de vie d'une connexion TCP

Ouverture en trois temps (SYN, SYN/ACK, ACK), échange de données, puis fermeture négociée (FIN, ACK, FIN, ACK).

L'établissement d'une connexion TCP se fait en trois segments (three-way handshake) :

  1. Le client envoie un segment SYN (synchronisation) avec son numéro de séquence initial.
  2. Le serveur répond par un SYN/ACK acquittant le SYN du client et proposant son propre numéro de séquence.
  3. Le client confirme par un ACK.

La fermeture est également négociée, en quatre segments (chaque extrémité ferme son propre sens de communication). Cette symétrie explique l'apparition de l'état TIME_WAIT côté client, qui persiste environ deux minutes après la fermeture.

3.3 — États d'une socket TCP

Schéma 2 — États d'une socket TCP (côté serveur)

États principaux : CLOSED, LISTEN, SYN_RECEIVED, ESTABLISHED, CLOSE_WAIT, LAST_ACK. Les transitions correspondent aux appels système et aux segments reçus.

L'état ESTABLISHED est le seul où les données circulent normalement. L'état CLOSE_WAIT indique que le pair a fermé son côté, mais que l'application locale n'a pas encore appelé close().

À retenir — côté serveur, l'ordre des appels système est socket → bind → listen → accept. Côté client : socket → connect.

4. API Python : le module socket

4.1 — Fonctions principales

AppelRôleCôté
socket.socket(famille, type) Crée une socket Client et serveur
bind((ip, port)) Attache la socket à une adresse locale Serveur
listen(n) Met la socket en écoute, avec une file d'attente de n connexions Serveur
accept() Accepte une connexion, renvoie une nouvelle socket pour communiquer Serveur
connect((ip, port)) Se connecte à un serveur Client
send(data) Envoie des octets — peut en envoyer moins que demandé Client et serveur
sendall(data) Envoie tous les octets, ou lève une exception Client et serveur
recv(taille) Reçoit jusqu'à taille octets Client et serveur

settimeout(secondes) Fixe un délai maximal sur les opérations bloquantes Client et serveur
setsockopt(niveau, option, valeur) Configure une option de la socket Client et serveur

4.2 — send() versus sendall()

send() renvoie le nombre d'octets effectivement envoyés, qui peut être inférieur à la taille demandée (notamment si la mémoire tampon est pleine). sendall() boucle en interne jusqu'à avoir tout envoyé. 

# send() — nécessite une boucle si l'envoi est partiel
total = 0
while total < len(donnees):
    envoye = sock.send(donnees[total:])
    total += envoye

# sendall() — équivalent, mais géré par la bibliothèque
sock.sendall(donnees)
Recommandation — utiliser sendall() dans presque tous les cas. send() ne se justifie que pour un contrôle fin du débit.

4.3 — Données binaires et encodage

send() et recv() manipulent des bytes, jamais des str. La conversion se fait par encode() et decode(), avec un encodage explicite (utf-8 en général). 

message = "Bonjour"
donnees = message.encode("utf-8")     # str → bytes
texte   = donnees.decode("utf-8")     # bytes → str

assert message == texte
assert isinstance(donnees, bytes)

L'encodage par défaut de encode() est utf-8, mais il vaut mieux le rendre explicite pour éviter toute ambiguïté entre plateformes.

4.4 — Sémantique de recv()

Propriété — recv(n) renvoie jusqu'à n octets. TCP étant un flux, il peut rendre moins que n, et il peut fragmenter un envoi en plusieurs réceptions.

Deux conséquences pratiques :

  • un appel à send() ne correspond pas nécessairement à un appel à recv() ;
  • pour lire une quantité fixe d'octets, il faut boucler jusqu'à l'avoir obtenue.
def recv_exact(sock, n):
    """Lit exactement n octets, ou lève une erreur si la connexion se ferme."""
    donnees = b""
    while len(donnees) < n:
        morceau = sock.recv(n - len(donnees))
        if not morceau:
            raise ConnectionError("connexion fermée avant réception complète")
        donnees += morceau
    return donnees

4.5 — Détection de fermeture

recv() qui renvoie b"" signale que le pair a fermé la connexion. C'est la méthode canonique de détection, et elle ne lève pas d'exception. 

data = sock.recv(1024)
if data == b"":
    print("connexion fermée par le pair")

4.6 — Timeout

Par défaut, les opérations bloquantes (accept(), recv()) attendent indéfiniment. On fixe un délai maximal avec settimeout(). 

sock.settimeout(5.0)   # 5 secondes

try:
    data = sock.recv(1024)
except socket.timeout:
    print("délai dépassé")

settimeout(None) rétablit le mode bloquant. Un timeout de 0 place la socket en mode non bloquant.

4.7 — Réutilisation d'adresse : SO_REUSEADDR

Après la fermeture d'un serveur, le port reste dans l'état TIME_WAIT pendant environ deux minutes. Tenter de relancer le serveur immédiatement échoue avec OSError: Address already in use. 

srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 9000))

Cette option autorise la réutilisation immédiate d'une adresse locale en TIME_WAIT. Elle est indispensable en développement.

4.8 — Exemple complet : serveur et client TCP

Ce couple d'exemples illustre l'ensemble des notions ci-dessus. Il servira de référence pour les TP.

Serveur

import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 9000))
srv.listen(5)
print("[serveur] écoute sur 9000")

conn, addr = srv.accept()
conn.settimeout(10)
print(f"[serveur] client {addr}")

while True:
    data = conn.recv(1024)
    if not data:                       # b"" : client déconnecté
        print("[serveur] client déconnecté")
        break
    print(f"[serveur] reçu {len(data)} octets")
    conn.sendall(data)

conn.close()
srv.close()

Client

import socket

cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
cli.settimeout(5)
cli.connect(("127.0.0.1", 9000))
print("[client] connecté")

message = "Bonjour serveur"
cli.sendall(message.encode("utf-8"))

reponse = cli.recv(1024)
if reponse == b"":
    print("[client] connexion fermée")
else:
    print(f"[client] réponse : {reponse.decode('utf-8')}")

cli.close()

5. Erreurs réseau courantes

Un programme réseau doit anticiper les erreurs. Contrairement à un programme local, il dépend d'un environnement non maîtrisé : le réseau, l'autre machine, la disponibilité du service.

5.1 — Catalogue des erreurs

ErreurCauseRemède
ConnectionRefusedError Serveur non lancé, port erroné, ou rejet explicite Vérifier l'état du serveur, le port
TimeoutError / socket.timeout Pas de réponse dans le délai imparti settimeout(), try/except
OSError: Address already in use Port encore occupé (état TIME_WAIT) setsockopt(SO_REUSEADDR, 1)
ConnectionResetError Fermeture brutale par le pair (RST) Gérer dans try/except, fermer proprement
BrokenPipeError Écriture sur une connexion déjà fermée Détecter recv() == b"" avant d'écrire
OSError: [Errno 101] Network is unreachable Route absente vers la destination Vérifier la configuration réseau
socket.gaierror Échec de résolution de nom (DNS) Vérifier le nom, la connexion DNS

5.2 — Structure canonique d'un serveur robuste

import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 9000))
srv.listen(5)

try:
    conn, addr = srv.accept()
    conn.settimeout(10)

    while True:
        try:
            data = conn.recv(1024)
        except socket.timeout:
            print("timeout sur recv()")
            break

        if not data:
            break

        try:
            conn.sendall(data)
        except BrokenPipeError:
            print("le pair a fermé la connexion")
            break

except ConnectionResetError:
    print("connexion réinitialisée par le pair")
finally:
    try: conn.close()
    except NameError: pass
    srv.close()

Le bloc finally garantit la libération des ressources, même en cas d'erreur. Le try/except NameError protège le cas où accept() aurait échoué avant l'affectation de conn.

6. UDP : le mode non connecté

6.1 — Propriétés

PropriétéUDP
TypeNon connecté (datagrammes)
FiabilitéAucune garantie
OrdreNon préservé
Frontières de messagePrésentes — un envoi = un datagramme
Contrôle de fluxNon
Contrôle de congestionNon
Constante PythonSOCK_DGRAM

6.2 — API spécifique

AppelRôle
sendto(data, (ip, port))Envoie un datagramme à une adresse
recvfrom(taille)Reçoit un datagramme et l'adresse de l'expéditeur

UDP ne comporte ni listen(), ni accept(). La socket serveur est simplement attachée à un port par bind(). connect() existe mais reste optionnel : il ne fait que fixer l'adresse par défaut d'envoi.

6.3 — Exemple complet : serveur et client UDP

Serveur UDP

import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
srv.bind(("0.0.0.0", 9001))
print("[serveur UDP] écoute sur 9001")

while True:
    data, addr = srv.recvfrom(1024)
    print(f"[serveur UDP] {addr} : {data!r}")
    srv.sendto(data, addr)

Client UDP

import socket

cli = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
cli.settimeout(3)

message = "ping UDP"
cli.sendto(message.encode("utf-8"), ("127.0.0.1", 9001))

try:
    reponse, _ = cli.recvfrom(1024)
    print(f"[client UDP] réponse : {reponse.decode('utf-8')}")
except socket.timeout:
    print("[client UDP] pas de réponse")

cli.close()

6.4 — Différences fondamentales TCP / UDP

CritèreTCPUDP
ÉtablissementOui (handshake)Non
Envoisend, sendallsendto
Réceptionrecvrecvfrom
FrontièresNonOui
Détection de perteAutomatiqueAucune
Signalement de fermeturerecv() == b""Impossible à détecter
Cas d'usageHTTP, SSH, transfert de fichiersDNS, VoIP, jeux, streaming
Propriété — en UDP, l'absence de réponse n'est pas détectable par le protocole. Si un datagramme est perdu, l'application attend indéfiniment. Seul un timeout applicatif permet de détecter la perte.

6.5 — Taille d'un datagramme

La taille maximale d'un datagramme UDP est théoriquement de 65507 octets (limite du protocole IP). En pratique, on dépasse rarement 1472 octets (MTU Ethernet 1500 – en-têtes IP et UDP). Au-delà, la fragmentation IP dégrade les performances et augmente les risques de perte.

7. Pièges et erreurs courantes

Cette section recense les erreurs les plus fréquentes rencontrées par les étudiants lors de l'écriture de programmes réseau. Chaque piège est présenté sous la forme symptôme → cause → remède.

7.1 — Piège : oublier d'encoder avant send()

Symptôme — TypeError: a bytes-like object is required, not 'str'.

Cause — send() et sendall() n'acceptent que des bytes. Un str ne passe pas.

Remède — data.encode("utf-8") avant l'envoi, data.decode("utf-8") après la réception.

7.2 — Piège : croire que recv(n) renvoie n octets

Symptôme — un message long arrive tronqué, ou une partie du message suivant est collée au premier.

Cause — TCP est un flux. recv(n) renvoie jusqu'à n octets, pas exactement n.

Remède — boucler jusqu'à avoir la quantité désirée, ou utiliser un délimiteur de message, ou préfixer par une longueur.

7.3 — Piège : confondre accept() et la socket de communication

Symptôme — le serveur ne peut pas accepter un second client.

Cause — accept() renvoie une nouvelle socket dédiée à la communication. La socket d'écoute reste disponible pour d'autres accept(). Utiliser la socket d'écoute pour recv() est une erreur.

Remède — bien distinguer srv (écoute) et conn (communication).

7.4 — Piège : oublier SO_REUSEADDR

Symptôme — OSError: [Errno 98] Address already in use au redémarrage du serveur.

Cause — le port est encore en TIME_WAIT après la fermeture.

Remède — appeler setsockopt(SO_REUSEADDR, 1) avant bind().

7.5 — Piège : ne pas gérer la fermeture

Symptôme — boucle infinie dans le serveur, ou exception BrokenPipeError lors d'un envoi.

Cause — recv() qui renvoie b"" n'est pas détecté, ou on écrit sur une socket fermée.

Remède — tester if not data: break après chaque recv(). Envelopper les envois dans un try/except BrokenPipeError.

7.6 — Piège : bloquer indéfiniment sur recv()

Symptôme — le programme ne répond plus, impossible de l'interrompre proprement.

Cause — recv() sans timeout attend indéfiniment.

Remède — settimeout(N) et gérer socket.timeout dans un try/except.

7.7 — Piège : croire qu'UDP signale les pertes

Symptôme — le client UDP attend indéfiniment alors que le serveur n'est pas lancé.

Cause — UDP n'a aucun mécanisme de retour. Un datagramme vers un port fermé génère un message ICMP port unreachable, mais celui-ci n'est pas remonté à l'application par défaut.

Remède — prévoir un timeout applicatif et une stratégie de retransmission si nécessaire.

7.8 — Piège : confondre send() et sendall()

Symptôme — un gros message est tronqué, sans erreur apparente.

Cause — send() peut envoyer moins que demandé. Ignorer la valeur de retour conduit à une perte silencieuse.

Remède — utiliser sendall().

7.9 — Piège : réutiliser une socket fermée

Symptôme — OSError: [Errno 9] Bad file descriptor.

Cause — une socket fermée ne peut plus être utilisée. Elle doit être recréée.

Remède — vérifier le cycle de vie. En cas de reconnexion, créer une nouvelle socket.

7.10 — Piège : recv() avec une taille trop petite

Symptôme — les messages longs sont tronqués.

Cause — recv(10) ne lit que 10 octets au maximum, le reste reste dans le tampon.

Remède — dimensionner le tampon en fonction du protocole, ou boucler jusqu'à épuisement.

11. TP 4 — Mini-protocole applicatif

Difficile

Objectif

Concevoir et implémenter un protocole applicatif simple : un serveur de calcul qui reçoit des opérations et renvoie le résultat ou un message d'erreur. Ce TP mobilise l'ensemble des notions de la journée.

Spécification du protocole

RequêteRéponse attendue
add 3 58
sub 10 46
mul 6 742
div 10 0ERROR division par zéro
add 3ERROR format invalide
foo 1 2ERROR opération inconnue

Les messages sont encodés en UTF-8. Chaque requête tient sur une ligne terminée par un saut de ligne. Le serveur répond par une ligne, terminée également par un saut de ligne.

Cahier des charges

Serveur TCP — serveur_calc.py

  • Écouter sur le port 9002.
  • Accepter une connexion, puis traiter les requêtes successives jusqu'à fermeture par le client.
  • Pour chaque requête : décoder, analyser (split()), exécuter l'opération, produire une réponse.
  • Gérer les erreurs de format et les opérations inconnues.
  • Utiliser SO_REUSEADDR et un timeout.

Client TCP — client_calc.py

  • Se connecter à 127.0.0.1:9002.
  • Boucler : lire une ligne au clavier, l'envoyer, attendre la réponse, l'afficher.
  • Quitter sur la commande quit.

Extensions

  • Accepter des nombres flottants.
  • Ajouter l'opération pow.
  • Reprendre le même protocole en UDP et comparer le comportement en cas de perte.
  • Ajouter un compteur de requêtes traitées côté serveur.

Question de synthèse

Le protocole est ici textuel, avec des messages séparés par des sauts de ligne. Quels sont les avantages et les inconvénients de ce choix par rapport à un format binaire avec un champ de longueur explicite ?

12. À retenir — Jour 1

  • Une socket est une extrémité de communication identifiée par un triplet (adresse IP, port, protocole).
  • TCP est connecté, fiable, ordonné, sans frontières de message. UDP est non connecté, non fiable, avec frontières de message.
  • Côté serveur TCP : socket → bind → listen → accept. Côté client TCP : socket → connect.
  • Côté serveur UDP : socket → bind. Côté client UDP : socket seul.
  • send() et recv() manipulent des bytes. Conversion par encode() et decode().
  • sendall() est préférable à send() : il garantit l'envoi complet ou lève une exception.
  • recv() peut renvoyer moins que la taille demandée. Pour lire une quantité fixe, boucler.
  • recv() == b"" signale la fermeture de la connexion par le pair.
  • Prévoir systématiquement settimeout(), try/except et finally: close().
  • SO_REUSEADDR évite l'erreur de port occupé au redémarrage.
  • UDP ne signale pas les pertes : seul un timeout côté application permet de les détecter.
  • accept() renvoie une nouvelle socket, distincte de la socket d'écoute.
