Séquence 1

1. Pourquoi un serveur séquentiel bloque

1.1 — Le serveur du Jour 1, en une phrase

Le serveur écrit au Jour 1 exécute une boucle très simple : il attend un client, le sert jusqu'à ce que celui-ci ferme la connexion, puis attend le suivant. Cette structure fonctionne, mais elle présente un défaut fondamental : elle traite les clients strictement l'un après l'autre.

Pour bien comprendre le problème, il faut se représenter ce que fait concrètement le programme. Un programme Java s'exécute dans un thread — un fil d'exécution — qui déroule ses instructions les unes à la suite. À chaque instant, il est exactement à un endroit du code. S'il est dans une instruction qui attend quelque chose, il ne peut pas en même temps être ailleurs.

L'analogie naturelle est celle d'un guichet unique dans une administration. Un employé, un guichet. Le client A arrive, l'employé le sert. Pendant tout ce temps, le client B attend dehors, même si le dossier du client A est terminé depuis longtemps et que l'employé est simplement en train d'attendre que le client A signe un papier. L'employé pourrait servir B, mais il est occupé à attendre.

Analogie — un serveur séquentiel est un guichet unique. Le guichetier attend que le client A ait fini, même si c'est juste pour récupérer une signature. Le client B fait la queue dehors, sans que personne ne s'occupe de lui.

1.2 — Les deux endroits exacts où le serveur bloque

Le serveur du Jour 1 contient deux instructions qui peuvent bloquer. Comprendre chacune séparément est essentiel pour la suite.

Premier blocage : accept()

ServerSocket.accept() est une instruction bloquante : si aucun client n'est en attente de connexion, l'appel ne rend pas la main. Le programme est suspendu à cette ligne. Il ne passe pas à l'instruction suivante, il ne lit rien, il ne calcule rien. Il attend.

Cette attente est normale et souhaitable au démarrage : le serveur n'a rien à faire tant qu'aucun client ne se connecte. Mais elle devient un problème dès qu'un client est déjà en cours de traitement, parce que accept() ne sera pas appelé avant que le traitement soit fini.

Second blocage : read()

InputStream.read() est également bloquante : si aucun octet n'est disponible dans le tampon du système, l'appel ne rend pas la main. Le programme attend que le client envoie quelque chose. C'est ce qui se passe quand votre serveur attend un message : il ne fait rien d'autre que d'attendre, indéfiniment si nécessaire.

La conséquence est plus subtile que pour accept(). Pendant que le serveur attend un message du client A, il pourrait très bien être en train de lire un message du client B. Mais il ne peut pas : il est figé sur le read() du client A. Un seul read() à la fois, donc un seul client à la fois.

Schéma 1 — Blocage dans accept()

Le serveur traite le client A. Le client B se connecte et envoie même un message, mais son accept() n'est pas encore appelé : il attend dans la file du système, sans que le serveur ne sache qu'il existe.

1.3 — Ce que « bloquant » veut dire techniquement

Le mot bloquant a un sens précis en programmation système. Une opération est bloquante si le thread qui l'exécute est retiré du processeur jusqu'à ce qu'un événement extérieur se produise. Le système d'exploitation place le thread dans un état d'attente, et le processeur peut alors exécuter d'autres threads.

Cela signifie que bloquer n'est pas consommer du CPU. Un serveur qui attend dans accept() ne fait rien du tout — il ne consomme ni processeur, ni mémoire active. Il est simplement suspendu.

Pourquoi est-ce important ? Parce que si l'on veut que le serveur puisse être réactif malgré les opérations bloquantes, il faut soit les rendre non bloquantes, soit avoir plusieurs threads (chacun pouvant être bloqué sur son propre read()).

Propriété — rendre un échange non bloquant ne signifie pas empêcher le thread de s'arrêter. Cela signifie que le programme, dans son ensemble, peut continuer à progresser sur d'autres tâches pendant qu'une opération d'E/S est en attente. Deux mécanismes existent : plusieurs threads, ou des opérations d'E/S non bloquantes (NIO).

1.4 — Ce qu'on va construire aujourd'hui

Trois étapes, dans cet ordre :

  1. Rendre un échange non bloquant : un seul client, mais le programme n'est pas figé pendant la lecture.
  2. Accepter plusieurs clients : plusieurs threads, un par client, pour que chaque client ait sa propre opération bloquante indépendante.
  3. Organiser la communication : les clients peuvent s'échanger des messages par groupes, avec la synchronisation nécessaire.

Séquence 2

2. Threads Java

2.1 — Définition d'un thread

Un thread (fil d'exécution) est une unité d'exécution à l'intérieur d'un processus. Un processus peut contenir plusieurs threads, qui s'exécutent concurremment : ils partagent la mémoire du processus (mêmes variables, mêmes objets), mais ont chacun leur propre pile d'appels — c'est-à-dire leur propre « position » dans le code à un instant donné.

Reprenons l'analogie du guichet. Un serveur séquentiel a un guichetier. Un serveur multi-thread en a plusieurs, qui travaillent en parallèle dans la même agence. Ils partagent les mêmes dossiers (la mémoire), mais chacun sert un client à un instant donné. Quand un guichetier attend une signature, les autres peuvent continuer à servir leurs clients respectifs.

Analogie — un thread est un guichetier supplémentaire dans la même agence. Tous voient les mêmes dossiers, mais chacun travaille à son rythme, en parallèle des autres.

En Java, un thread est représenté par la classe java.lang.Thread. Cette classe encapsule l'état du thread (son nom, sa priorité, son état d'exécution) et fournit les méthodes pour le démarrer, l'arrêter, l'attendre.

2.2 — Deux manières de créer un thread

Java permet de définir ce qu'un thread doit faire de deux manières. La différence est importante à comprendre.

Approche 1 — Hériter de Thread

On crée une sous-classe de Thread et on redéfinit la méthode run(). C'est le code qui sera exécuté quand le thread démarrera. 

class MonThread extends Thread {
    @Override
    public void run() {
        System.out.println("dans le thread " + getName());
    }
}

// Utilisation
MonThread t = new MonThread();
t.start();   // démarre le thread

Cette approche est simple mais limitante : en Java, une classe ne peut hériter que d'une seule classe. Si MonThread hérite de Thread, elle ne peut pas hériter d'une autre classe utile (par exemple une classe métier).

Approche 2 — Implémenter Runnable

On crée une classe (ou une lambda) qui implémente l'interface Runnable. Cette interface n'a qu'une méthode : run(). On passe ensuite l'instance à un Thread. 

class MaTache implements Runnable {
    @Override
    public void run() {
        System.out.println("dans le Runnable");
    }
}

// Utilisation
Thread t = new Thread(new MaTache());
t.start();

// Avec une lambda (plus concis, car Runnable est une interface fonctionnelle)
Thread t2 = new Thread(() -> System.out.println("dans une lambda"));
t2.start();

Cette approche est recommandée par la documentation Java, parce qu'elle sépare la tâche (ce qui doit être fait, défini par Runnable) du thread (le mécanisme d'exécution, défini par Thread). Cette séparation sera cruciale quand on utilisera un pool de threads.

Propriété — start() crée un nouveau thread et exécute run() dedans. run() appelé directement exécute le code dans le thread courant — ce n'est pas la même chose. C'est l'erreur la plus fréquente chez les débutants.

2.3 — Cycle de vie d'un thread

Un thread Java passe par plusieurs états au cours de sa vie. Comprendre ces états permet de diagnostiquer les problèmes de concurrence.

Schéma 2 — États d'un thread Java

Un thread commence en NEW, devient RUNNABLE après start(), peut passer par BLOCKED / WAITING / TIMED_WAITING selon les opérations, et finit en TERMINATED quand run() se termine.

ÉtatSignification
NEW Thread créé mais pas encore démarré
RUNNABLE Thread en cours d'exécution, ou prêt à s'exécuter
BLOCKED Thread en attente d'un verrou (voir séquence 5)
WAITING Thread qui attend indéfiniment un signal d'un autre thread (wait(), join())
TIMED_WAITING Thread qui attend avec un délai (sleep(), wait(timeout))
TERMINATED Thread terminé (fin de run())

2.5 — Rendre un échange non bloquant par deux threads

Maintenant qu'on sait créer des threads, on peut résoudre le premier problème identifié : l'échange avec un seul client est bloqué pendant la lecture. Un programme qui lit dans une boucle ne peut pas, en même temps, lire le clavier ou envoyer un message.

La solution est d'avoir deux threads :

  • un thread de lecture, qui appelle read() en boucle et affiche les messages reçus ;
  • un thread d'écriture, qui lit l'entrée clavier et envoie les messages au serveur.

Les deux threads partagent le Socket, mais pas les mêmes opérations : l'un utilise getInputStream(), l'autre getOutputStream(). Comme les opérations bloquent dans des threads différents, l'un n'empêche pas l'autre de progresser.

Schéma 3 — Échange non bloquant par deux threads

Un thread lit en permanence (read()), un autre écrit quand l'utilisateur le demande. Les deux opérations ne se bloquent pas mutuellement, car elles s'exécutent dans deux threads distincts.

3. Serveur multi-clients par thread

3.1 — Le principe

On a vu qu'un client seul avec deux threads peut échanger sans se bloquer. Le même raisonnement s'applique côté serveur : si chaque client traité dans son propre thread, alors le blocage d'un client n'empêche pas les autres d'être servis.

L'idée est la suivante : le thread principal reste dans une boucle d'acceptation. À chaque connexion, il crée un nouveau thread chargé de traiter ce client, et retourne immédiatement à accept(). Le nouveau thread, lui, gère son client de bout en bout : lecture des messages, envoi des réponses, fermeture en fin de connexion.

Schéma 4 — Serveur multi-clients par thread

Le thread principal accepte les connexions et crée un thread de traitement pour chacune. Chaque thread de traitement gère son client de manière autonome, sans bloquer les autres.

3.2 — Structure canonique

Le serveur ressemble à ceci : 

ServerSocket server = new ServerSocket(9000);
while (true) {
    Socket conn = server.accept();     // bloquant
    Thread t = new Thread(new ClientHandler(conn));
    t.start();                         // non bloquant
}
// le thread principal retourne immédiatement à accept()

La classe ClientHandler implémente Runnable et contient toute la logique de traitement d'un client. Elle est indépendante des autres : elle ne partage avec elles que ce que le serveur décide explicitement de partager (par exemple, la liste des clients connectés — voir séquence 5). 

public class ClientHandler implements Runnable {
    private final Socket socket;

    public ClientHandler(Socket socket) {
        this.socket = socket;
    }

    @Override
    public void run() {
        try (socket;
             InputStream in = socket.getInputStream();
             OutputStream out = socket.getOutputStream()) {

            byte[] buffer = new byte[1024];
            int n;
            while ((n = in.read(buffer)) != -1) {
                out.write(buffer, 0, n);
                out.flush();
            }
        } catch (IOException e) {
            System.err.println("client " + socket + " : " + e.getMessage());
        } finally {
            System.out.println("client " + socket + " déconnecté");
        }
    }
}

3.3 — Ce qui est partagé, ce qui ne l'est pas

Une erreur fréquente est de croire que tout est partagé entre threads. En réalité, il faut distinguer :

ÉlémentPartagé ?Conséquence
ServerSocket Oui (un seul) Le thread principal l'utilise seul. Les threads de traitement n'y touchent pas.
Socket du client Non Un par client, utilisé par un seul thread de traitement.
Flux d'entrée/sortie du client Non Un par client, un seul thread y accède.
Variables d'instance du handler Non Chaque handler a ses propres valeurs.
Structures globales (liste des clients, compteur) Oui Doivent être protégées (voir séquence 5).

Tant qu'on ne partage rien, un serveur multi-thread est naturellement sûr. Les problèmes commencent dès qu'on introduit une structure commune (compteur, liste, etc.).

3.4 — Le compteur de clients

Pour illustrer, on peut vouloir compter le nombre de clients connectés. Une première idée est d'utiliser un int statique : 

private static int nbClients = 0;

// à la connexion
nbClients++;    // ← problème : non atomique
// à la déconnexion
nbClients--;    // ← problème : non atomique

Cette opération nbClients++ n'est pas atomique : elle se décompose en trois instructions (lire, incrémenter, écrire). Deux threads peuvent s'entrelacer entre ces instructions et perdre une incrémentation. On verra en séquence 5 comment corriger cela. Pour l'instant, on se contente de l'afficher.

Séquence 4

4. Pool de threads

4.1 — Pourquoi le thread-par-client ne suffit pas

La stratégie « un thread par client » fonctionne bien pour quelques dizaines de connexions. Mais elle a trois limites qui deviennent rédhibitoires pour un serveur réel.

Limite 1 — Coût mémoire

Chaque thread Java a une pile d'appels. Par défaut, cette pile fait entre 512 Ko et 1 Mo. Pour 1000 clients, cela représente 500 Mo à 1 Go de mémoire, uniquement pour les piles. À cela s'ajoutent les objets alloués par le code de chaque thread.

Limite 2 — Coût de création et de destruction

Créer un thread n'est pas gratuit : le système d'exploitation doit allouer les ressources, enregistrer le thread auprès du planificateur, etc. Détruire un thread aussi. Pour un serveur de chat où les clients se connectent et se déconnectent souvent, ce coût devient significatif.

Limite 3 — Plafond du système

Le système d'exploitation impose une limite pratique au nombre de threads simultanés (de l'ordre de quelques milliers selon les configurations). Au-delà, la JVM lève OutOfMemoryError: unable to create native thread.

Analogie — au lieu d'embaucher un guichetier pour chaque client puis le licencier à la fin, on embauche un nombre fixe de guichetiers. Les clients font la queue, et chaque guichetier traite le client suivant dès qu'il a fini le précédent. C'est un pool de threads.

4.2 — Le principe du pool

Un pool de threads est un ensemble de threads créés une fois pour toutes et réutilisés pour exécuter des tâches successives. Les tâches qui arrivent sont placées dans une file d'attente, et les threads disponibles les consomment une par une.

Schéma 5 — Pool de threads

Les tâches (connexions acceptées) sont placées dans une file d'attente. Un nombre fixe de threads les consomme une par une. Un thread qui termine une tâche reprend immédiatement la suivante dans la file.

4.3 — ExecutorService en Java

Java fournit le framework java.util.concurrent avec l'interface ExecutorService et la classe Executors qui propose des fabriques de pools. 

ExecutorService pool = Executors.newFixedThreadPool(10);

while (true) {
    Socket conn = server.accept();
    pool.submit(new ClientHandler(conn));   // ← remplace new Thread(...).start()
}

Le code est presque identique à la version thread-par-client. La différence est que submit() ne crée pas un nouveau thread : il place la tâche dans la file du pool. Un thread disponible la prendra.

MéthodeRôle
newFixedThreadPool(n)Pool à n threads fixes
newCachedThreadPool()Pool qui crée des threads à la demande, les réutilise 60 s
newSingleThreadExecutor()Pool à un seul thread (exécution séquentielle)
submit(Runnable)Soumet une tâche au pool
shutdown()Arrêt propre : termine les tâches en cours, refuse les nouvelles
shutdownNow()Arrêt immédiat : interrompt les tâches
awaitTermination(timeout, unit)Attend la fin de toutes les tâches

4.4 — Arrêt propre du pool

Un pool non arrêté maintient ses threads actifs, ce qui empêche la JVM de se terminer après la fin de main. Il faut explicitement appeler shutdown().

La manière la plus robuste est d'utiliser un shutdown hook : un thread enregistré auprès de la JVM, exécuté automatiquement à l'arrêt (Ctrl+C, fin de programme). 

Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    System.out.println("arrêt en cours…");
    pool.shutdown();
    try {
        if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
            pool.shutdownNow();
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
    }
}));

Séquence 5

5. Synchronisation et broadcast

5.1 — Le problème de la section critique

Tant que les threads ne partagent rien, tout va bien. Les problèmes commencent dès qu'ils accèdent à une même structure de données. On parle de section critique : un bloc de code qui accède à une ressource partagée et qui ne doit être exécuté que par un seul thread à la fois.

Reprenons l'exemple du compteur de clients. L'opération nbClients++ semble atomique, mais elle se décompose en réalité en trois instructions machine :

  1. lire la valeur de nbClients en mémoire ;
  2. incrémenter cette valeur dans un registre du processeur ;
  3. écrire la nouvelle valeur en mémoire.

Si deux threads exécutent nbClients++ en même temps, ils peuvent s'entrelacer : les deux lisent 5, les deux incrémentent à 6, les deux écrivent 6. Le compteur a augmenté de 1 au lieu de 2.

Analogie — deux guichetiers qui tiennent chacun un carnet de comptage différents, mais doivent reporter sur un tableau commun. Si les deux regardent le tableau (qui indique « 5 ») en même temps, puis écrivent chacun « 6 », le tableau indique 6 alors que deux clients ont été servis. L'information d'un des deux est perdue.

Schéma 6 — Accès concurrent à une liste

Deux threads modifient une liste partagée. Sans synchronisation, l'un peut voir un état intermédiaire produit par l'autre, ou produire un état incohérent.

5.2 — synchronized

Java fournit le mot-clé synchronized pour protéger une section critique. Il fonctionne sur le principe d'un verrou (lock) : un seul thread à la fois peut détenir le verrou et exécuter le code protégé. Les autres threads qui tentent d'entrer dans la section sont mis en état BLOCKED et attendent.

Sur une méthode

public synchronized void ajouter(PrintWriter out) {
    clients.add(out);
}

Ici, le verrou est posé sur this — l'instance courante. Un seul thread à la fois peut exécuter ajouter sur cette instance.

Sur un bloc

public void ajouter(PrintWriter out) {
    synchronized (this) {
        clients.add(out);
    }
}

Cette forme permet de ne protéger que la partie vraiment critique, pas toute la méthode. C'est souvent préférable pour la performance.

Sur un objet dédié

private final Object verrou = new Object();

public void ajouter(PrintWriter out) {
    synchronized (verrou) {
        clients.add(out);
    }
}

Cette forme est utile quand plusieurs sections critiques doivent utiliser le même verrou sans que ce verrou soit l'instance elle-même.

Propriété — deux blocs synchronized sur le même objet ne peuvent pas être exécutés simultanément par deux threads différents. Deux blocs sur des objets différents n'ont aucune relation entre eux. C'est l'erreur la plus fréquente quand on commence à utiliser la synchronisation.

5.3 — Le broadcast

Un broadcast consiste à envoyer un message à tous les clients d'un ensemble. C'est le mécanisme de base d'un serveur de chat, mais aussi de tout système de diffusion (notifications, alertes, etc.).

Côté Java, cela se traduit par :

  • maintenir une structure partagée contenant les flux de sortie de tous les clients ;
  • parcourir cette structure à chaque message à diffuser ;
  • écrire dans chaque flux.

Cette opération est doublement critique : la structure peut être modifiée par d'autres threads pendant le parcours (déconnexions), et deux threads peuvent vouloir diffuser en même temps. Il faut synchroniser. 

public class GestionClients {
    private final List<PrintWriter> clients = new ArrayList<>();

    public synchronized void ajouter(PrintWriter out) {
        clients.add(out);
    }

    public synchronized void retirer(PrintWriter out) {
        clients.remove(out);
    }

    public synchronized void diffuser(String message) {
        for (PrintWriter out : clients) {
            out.println(message);
            out.flush();
        }
    }
}

Les trois méthodes sont synchronized sur la même instance de GestionClients. Elles ne peuvent donc pas s'exécuter simultanément : pas de ConcurrentModificationException, pas de message perdu.

Limites de cette approche

Cette implémentation a un inconvénient : si un client est lent à recevoir, le flush() peut bloquer, et tout le broadcast est ralenti pour tous les autres clients. Pour un serveur réel, on préfère généralement des files d'attente par client avec un thread d'envoi dédié. C'est une optimisation qui dépasse le cadre de ce cours, mais il faut en connaître l'existence.

5.4 — Autres mécanismes de synchronisation

synchronized n'est pas le seul outil. Java propose plusieurs structures adaptées à des cas spécifiques :

ClasseUsage
AtomicInteger, AtomicLongCompteurs atomiques (pas besoin de synchronized)
CopyOnWriteArrayListListe qui se copie à chaque modification (lecture fréquente, écriture rare)
ConcurrentHashMapMap thread-safe avec un bon parallélisme
ReentrantLockVerrou explicite avec plus de contrôle que synchronized
BlockingQueueFile d'attente avec blocage quand vide/pleine

Pour le projet de la journée, synchronized sur GestionClients suffit. Les autres mécanismes seront utiles pour des projets plus ambitieux.

6. NIO en survol

6.1 — Le principe

Java propose une seconde API réseau, dite NIO (New I/O, apparue avec Java 1.4), fondée sur des canaux non bloquants et un sélecteur. L'idée est de renverser l'approche : au lieu qu'un thread attende une opération d'E/S, un unique thread surveille plusieurs canaux à la fois et est notifié quand l'un d'eux est prêt.

Concrètement, au lieu d'avoir un thread par client (chacun bloqué sur son read()), on a un seul thread qui interroge le sélecteur pour savoir quels canaux ont des données à lire. Il les lit alors sans jamais bloquer.

Schéma 7 — Modèle NIO

Un unique thread surveille plusieurs canaux via un sélecteur. Il est notifié quand un canal est prêt à lire ou à écrire, et traite alors uniquement ce canal.

7. Pièges et erreurs courantes

Cette section recense les erreurs les plus fréquentes rencontrées par les étudiants lors de l'écriture de programmes réseau multi-thread en Java. Chaque piège est présenté sous la forme symptôme → cause → remède.

7.1 — Appeler run() au lieu de start()

Symptôme — le code du thread s'exécute, mais séquentiellement, dans le thread principal. Le programme se bloque comme si on n'avait pas mis de thread du tout.

Cause — run() est une méthode ordinaire. L'appeler directement exécute le code dans le thread courant, pas dans un nouveau thread. Seul start() crée un nouveau thread.

Remède — toujours start().

7.2 — Oublier join()

Symptôme — le programme principal se termine avant les threads lancés, ou les résultats ne sont pas encore affichés.

Cause — les threads non-démons sont interrompus à la fin de la JVM. Si main se termine, ils n'ont pas le temps de finir.

Remède — join() sur les threads importants, ou awaitTermination() sur le pool.

7.3 — Fermer le socket dans le mauvais thread

Symptôme — SocketException: Socket closed dans un thread de traitement.

Cause — le thread principal (ou un autre thread) a fermé le socket pendant que le thread de traitement l'utilisait encore.

Remède — chaque thread ferme les sockets dont il est responsable. Le thread principal ne ferme que le ServerSocket.

7.4 — ConcurrentModificationException

Symptôme — exception levée lors d'un broadcast, si un client se déconnecte en même temps.

Cause — parcours d'une liste pendant qu'un autre thread la modifie.

Remède — synchroniser l'ajout, le retrait et le parcours ; ou utiliser CopyOnWriteArrayList.

7.5 — synchronized sur le mauvais objet

Symptôme — la protection ne fonctionne pas, malgré la présence de synchronized.

Cause — deux blocs synchronized sur deux objets différents ne se bloquent pas mutuellement. Si les threads accèdent à la même ressource via deux verrous distincts, il n'y a aucune exclusion.

Remède — tous les accès à la ressource partagée doivent utiliser le même verrou.

7.6 — Deadlock

Symptôme — le programme se fige, plus rien n'avance.

Cause — deux threads attendent chacun un verrou détenu par l'autre.

Remède — ordre strict d'acquisition des verrous, ou un seul verrou.

7.7 — Thread non-démon qui bloque la JVM

Symptôme — la JVM ne se termine pas, même après main.

Cause — des threads de traitement sont encore actifs. La JVM attend qu'ils terminent.

Remède — setDaemon(true) pour les threads auxiliaires, ou shutdown() explicite du pool.

7.8 — Pool non arrêté

Symptôme — la JVM ne se termine pas après main.

Cause — ExecutorService non arrêté maintient ses threads actifs.

Remède — pool.shutdown() dans un bloc finally ou un shutdown hook.

7.9 — Broadcast non synchronisé

Symptôme — messages perdus, ordre incohérent chez certains clients.

Cause — deux threads écrivent en même temps dans le même PrintWriter ou parcourent la liste sans verrou.

Remède — synchronized sur la méthode de diffusion, ou verrou par flux de sortie.

7.10 — Exception silencieuse dans un thread

Symptôme — un client déconnecté n'apparaît pas dans les logs, la liste des clients reste fausse.

Cause — une exception non gérée dans run() termine le thread silencieusement sans exécuter le nettoyage.

Remède — try/catch/finally dans run(), avec retrait de la liste dans finally.

8. À retenir — Jour 2

  • accept() et read() sont bloquants : un programme séquentiel ne peut traiter qu'un seul client à la fois.
  • Bloquer ne consomme pas de CPU : le thread est simplement suspendu.
  • Un thread est une unité d'exécution concurrente dans un processus. On le crée avec new Thread(Runnable) et on le démarre avec start().
  • Un échange non bloquant peut se faire par deux threads : un qui lit, un qui écrit.
  • Un serveur multi-clients par thread accepte une connexion puis délègue son traitement à un thread.
  • Un pool de threads (ExecutorService) borne le nombre de threads actifs et réutilise les threads terminés.
  • Une section critique se protège par synchronized, sur un verrou unique.
  • Le broadcast consiste à envoyer un message à tous les clients d'un ensemble. Il doit être synchronisé.
  • NIO (Selector, Channel) propose un modèle événementiel à un seul thread, adapté à un grand nombre de connexions peu actives.
